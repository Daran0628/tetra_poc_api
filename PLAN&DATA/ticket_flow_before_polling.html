번호표 발급 앞부분 흐름

JWT 서명부터 번호표 발급까지의 구간을 시간 순서로 풀어 그렸습니다. 가로축이 시간이고 같은 세로줄은 같은 시점입니다. 02·03·04는 우리가 만든 템플릿이고 모두 CloudFront로 서빙하며, API는 같은 호스트의 /api/* 경로로 ALB에 붙는 구성입니다. Redis 명령은 하나씩 박스로 나눴고, 점선 괄호로 묶인 명령들은 Lua 한 번으로 원자적으로 실행됩니다. 폴링은 이 그림의 범위 밖입니다.

좌우로 스크롤하면 시간이 흐릅니다. 박스에 마우스를 올리면 그 단계가 하는 일이 툴팁으로 나옵니다. 엣지 레인은 CloudFront입니다.

  • 가장 크게 몰리는 구간입니다. 번호표 요청 한 건이 Redis 명령 네 개(세션 확인, 번호 채번, 번호 기록, 집계 갱신)를 Lua로 묶어 실행하고, DB와 큐는 없습니다.
  • 부하 완화 장치입니다 (지터 0~2초).
  • 엣지(CloudFront)입니다. 요청 경로를 보고 /api/*는 ALB로, 화면 요청은 테넌트 콘텐츠 S3로 보냅니다. 응답은 같은 길로 돌아오며 그림에서는 생략했습니다.
  • 점선 괄호는 Lua 한 번으로 묶여 원자적으로 실행되는 명령들입니다.
  • 점선 메모는 그 명령에서 갈라지는 분기를 설명합니다.
  • ↑사전 스케일링 후보 Pod입니다. 시점, 트리거, 범위는 아직 정하지 않았습니다.

구간별로 읽는 법

  • 진입(t1~t15): 테넌트가 서명한 JWT가 쿼리로 엣지를 거쳐 API에 도착하고, API가 공개키로 검증한 뒤 진입 Lua가 jti 재사용을 막고 세션을 찾거나 만듭니다. 세션 ID는 쿠키로 내려가고, 302를 따라 대기방 페이지가 테넌트 콘텐츠 S3에서 옵니다. 이 구간의 MySQL은 공개키를 읽기만 합니다.
  • 대기방에서 버튼까지(t16~t18): 약 1시간 뒤 카운트다운이 끝나면 버튼이 활성화되고, 지터 0~2초를 기다린 뒤 03 화면에 진입합니다. 서버는 관여하지 않습니다.
  • 번호표 요청(t19~t26): 이 시스템에서 가장 크게 몰리는 구간입니다. 같은 호스트의 /api/*로 쿠키와 함께 도착하고, 시작 시각을 앱 메모리에서 확인한 뒤 번호표 Lua로 세션 확인부터 집계 갱신까지 한 번에 처리해 번호를 응답합니다.

배포 구조 (CloudFront)

02, 03, 04는 우리 개발 부서가 만든 정적 템플릿(HTML, CSS, JS)입니다. 템플릿은 공용 버킷에서 그대로 서빙하지 않고, 이벤트를 만들 때 테넌트 콘텐츠 버킷으로 복사합니다. 02·03·04가 모두 복사되고, 테넌트가 올린 배너 같은 이미지(assets)도 같은 버킷에 들어갑니다. S3 정책은 기존과 같아서 버킷은 비공개이고 CloudFront만 읽습니다(OAC). 커스텀 업로드는 없고 JS는 전부 우리 코드입니다. 테넌트마다 distribution 하나를 두고 대체 도메인은 *.{tenant id}.루트도메인이며, 이벤트는 {event id}.{tenant id}.루트도메인 호스트로 들어옵니다. 같은 호스트 아래에서 경로로 오리진을 나눕니다.

경로오리진내용
/api/*ALB진입, 번호표, 쿠폰 받기 등 API. POST 허용, 캐시 끔, 쿠키와 쿼리 전달.
/*테넌트 콘텐츠 S302·03·04 템플릿 복사본과 이미지 assets. 호스트의 {event id}로 버킷 안의 파일 위치를 고릅니다.
  • 세 화면과 API가 같은 호스트라서 세션 쿠키가 모두에 자동으로 붙습니다. 화면의 JS는 세션 ID를 알 필요가 없고, 쿠키는 HttpOnly라 읽을 수도 없습니다.
  • 이벤트 식별: 02·03·04 코드는 location.hostname에서, API는 요청 호스트에서 event_id를 알아냅니다.
  • 호스트 이름의 {event id}로 버킷 안의 파일 위치를 고르는 일(템플릿 복사본과 이미지 모두)은 CloudFront Function(과 KeyValueStore)이 후보입니다. 문서에는 이미 이 둘로 호스팅 기간을 엣지에서 확인한다고 되어 있습니다. 버킷이 테넌트마다 하나인지 이벤트마다 하나인지에 따라 구성이 달라집니다.
  • 템플릿을 복사하는 방식은 문서의 기존 흐름(템플릿 버킷의 파일을 이벤트 승인 때 live 버킷으로 반영)과 같은 모양입니다. 복사본은 복사한 시점의 버전이라, 템플릿을 고치면 이미 복사된 이벤트에는 다시 복사해야 반영됩니다.
  • 인증서와 DNS는 테넌트마다 와일드카드 인증서(CloudFront용은 us-east-1)와 와일드카드 DNS 레코드 하나면 되고, 이벤트가 늘어도 추가 작업이 없습니다.
  • JS·CSS는 파일명에 해시를 넣어 길게, index.html은 짧게 캐시하고, 화면을 SPA로 만들면 새로고침 때의 403/404를 index.html로 돌려줍니다.
  • 테넌트가 올리는 파일은 이미지뿐이고, 테넌트가 JS 파일을 덮어쓸 수 없도록 버킷 쓰기는 우리 파이프라인만 하게 합니다(제안). 이미지 형식과 크기 제한은 미정입니다.

CloudFront Function의 동작 방식, /api/* 경로 규칙의 세부 옵션, 계정당 distribution 개수 한도는 제가 확실히 몰라서 AWS 문서 확인이 필요합니다.

이 그림의 가정

  • 02·03·04의 HTML, CSS, JS는 전부 우리 개발 부서가 만든 템플릿입니다. 커스텀 업로드는 없고, 테넌트는 배너 같은 이미지(assets)만 올릴 수 있습니다. 그래서 화면의 JS는 모두 우리 코드입니다. 템플릿은 우리가 테넌트 콘텐츠 버킷으로 복사해 주며 02·03·04가 모두 복사됩니다. S3 정책은 기존과 같습니다(비공개, CloudFront만 읽기).
  • 번호표 API는 재시도든 새로고침이든 호출될 때마다 INCR로 새 번호를 발급합니다. 버려진 번호는 구멍이 되고 서빙 커서는 구멍을 그냥 지나갑니다. 실제 입장 인원은 N × (1 − 구멍 비율)이며, 구멍 비율은 재발급 카운터를 전체 번호 발급 수로 나눠 계산합니다.
  • 진입은 Redis Lua 하나로 처리합니다. jti가 이미 있으면 거절하고(토큰 도용 방지), 같은 user_id의 세션이 이미 있으면 그 세션을 재사용하며(같은 사람의 중복 진입 방지), 둘 다 없을 때만 세션을 만들고 진입 카운터를 +1 합니다. 그래서 진입 카운터는 고유 사용자 수를 셉니다.
  • user_id는 테넌트가 회원마다 한 번 만들어 자기 매핑표에 저장하고 계속 재사용하는 랜덤 ID입니다. Tetra는 실제 회원 정보와 매핑을 갖지 않고, 발급 결과를 테넌트에 전달하면 테넌트가 매핑표로 실제 회원을 찾아 쿠폰을 지급합니다. 조건은 세 가지입니다. 테넌트 안에서 고유할 것, 실제 정보로 추측하거나 역산할 수 없는 값(UUID 등)일 것, 이벤트 기간 중에 바뀌지 않을 것. 그래서 JWT와 Tetra의 이력·로그에는 개인정보가 없고, 같은 사람은 항상 같은 user_id로 오므로 중복 진입 방지와 기존 세션 재사용이 성립합니다.
  • JWT는 테넌트 서버가 302로 보낸 주소의 쿼리(GET)로 전달합니다. 테넌트 구현이 가장 쉽고, user_id가 랜덤 ID라 로그에 남아도 개인정보가 없으며, jti는 한 번만 쓰이고 exp는 짧게(1~2분, 제안) 둡니다. 보완으로 302 응답에 Referrer-Policy: no-referrer와 HTTPS 전용을 두고, 쿼리 문자열을 로그에서 제외하는 것은 ALB와 CloudFront에서 가능한지 확인이 필요합니다. POST(자동 제출 폼)는 나중에 추가로 지원할 수 있는 선택지로 둡니다.
  • 세션 ID는 쿠키로 전달합니다. 진입 엔드포인트가 302 응답의 Set-Cookie로 내려 주고(HttpOnly, Secure, SameSite=Lax, 만료는 세션 TTL), 같은 호스트의 API를 부를 때 자동으로 붙습니다. 그래서 대기방이 뜨기 전까지 우리 Front JS는 관여하지 않습니다. 쿠키는 Domain 속성 없이(host-only) 내려서, 이벤트마다 호스트가 다르므로 다른 이벤트로 전달되지 않게 합니다(제안).
  • 02·03·04는 모두 테넌트별 CloudFront distribution(*.{tenant id}.루트도메인)에서 같은 호스트 아래 경로로 나뉘어 서빙됩니다. 그래서 세션을 04로 따로 잇는 방식이 필요 없습니다. API는 요청 호스트에서 얻은 event_id, 세션의 event_id, JWT의 tenant_id와 event_id가 서로 맞는지 확인합니다(제안). 요청 본문이 아니라 엣지가 정해 주는 호스트를 기준으로 삼습니다.
  • 번호표 요청은 Lua 스크립트 하나로 세션 확인, 번호 채번, 번호 기록, 집계 갱신을 처리합니다. 원자성 때문이 아니라 Redis 왕복 4번을 1번으로 줄이기 위한 성능 목적입니다. 재고 차감 Lua는 뒤쪽 쿠폰 발급 단계에서 씁니다.
  • 번호표 API는 서버 시각이 이벤트 시작 시각 전이면 Redis 호출 전에 거절합니다. 거절된 요청은 번호를 소모하지 않고 구멍도 만들지 않습니다. 카운트다운은 서버 시각 기준으로 보정합니다.
  • 지터는 0~2초이고 서버가 강제하지 않습니다. 우회하는 요청은 막지 못하는 것을 감수하며, 선착순은 서버 도착 순서 기준으로 2초 안에서는 순서가 섞입니다.
  • 진입은 대기방이 열려 있는 1시간에 고르게 들어온다고 가정합니다. 평균 초당 약 14건이라 진입 구간의 부담은 작고, 버스트 지점은 카운트다운 0 이후의 번호표 요청 하나입니다. 시작 직전에 쏠리는 경우(5분에 5만 명이면 초당 약 167건)도 부하 테스트 시나리오에 넣어 확인합니다.
  • Redis는 단일 노드 단일 샤드(클러스터 모드 미사용)로 두고 부족하면 노드 사양을 올립니다(스케일 업). 슬롯과 해시태그 제약이 없어서 카운터와 세션을 한 Lua에서 함께 다룰 수 있습니다.
  • PoC에서는 Redis를 EKS Pod 하나로 올립니다. 운영 배포에서 ElastiCache로 옮길지는 PoC 결과를 보고 정합니다. 두 경우 모두 같은 명령과 Lua를 쓰므로 전환은 접속 주소를 바꾸는 수준이라고 봅니다(제안). Pod는 앱 Pod와 노드를 나눠 쓰고 장애 조치가 없으며 재시작하면 세션과 카운터가 사라지므로, 이벤트가 진행되는 동안에는 재스케줄되지 않게 해야 합니다.
  • 발급이력은 쿠폰 받기 결과가 확정될 때 사용자당 행 하나를 INSERT합니다. 그래서 이 구간에는 MySQL 쓰기와 SQS, 워커가 없습니다. 진입만 하거나 번호만 받고 나간 사람은 사람별 기록 없이 집계 카운터로만 남깁니다.

함께 챙길 것 (제안)

  • 사용자별 요청 제한: 한 사용자가 번호표 요청을 반복하면 다른 사람의 대기열에 구멍을 만듭니다. 세션 단위로 요청 빈도를 제한합니다.
  • 클라이언트 재시도는 횟수 상한과 지수 백오프에 지터를 둡니다.
  • 발급 시점 검증과 폴링 응답은 서버 세션에 있는 번호를 기준으로 합니다. 브라우저가 들고 있는 예전 번호를 믿지 않습니다.
  • 집계 카운터는 Redis에만 있어서 장애 때 유실될 수 있습니다. 주기적으로 MySQL에 스냅샷할지, 유실을 감수할지 정합니다.
  • 세션 키와 user_id 연결 키는 TTL을 같이 주고, 한쪽만 남았을 때 어떻게 정리할지 정합니다. 기존 세션 조회 뒤에 그 세션이 실제로 있는지 확인하는 방식이 후보입니다.
  • JWT를 쿼리로 받으므로 테넌트가 exp를 1~2분으로 짧게 잡도록 연동 가이드에 적고, 302 응답에는 Referrer-Policy: no-referrer를 두며, 모든 구간을 HTTPS로만 받습니다.

결정된 것과 남은 것

결정

  • 재시도와 새로고침 모두 새 번호를 발급하고 구멍을 허용합니다.
  • 번호표 API가 서버 시각 기준으로 이벤트 시작 전 요청을 거절합니다.
  • 클라이언트 지터를 0~2초로 적용합니다. 서버 강제는 하지 않습니다.
  • jti(같은 토큰 재사용 방지)와 user_id(같은 사람의 중복 진입 방지)를 둘 다 사용합니다. 같은 사용자가 다시 진입하면 기존 세션을 재사용하고, 진입은 Lua 하나로 처리합니다.
  • 번호표 요청은 Lua 하나로 처리합니다.
  • JWT는 GET(302 + 쿼리)으로 전달합니다.
  • 세션 ID는 쿠키(HttpOnly, Secure, SameSite=Lax)로 전달합니다.
  • 02·03·04는 우리가 제공하는 템플릿만 사용하고, 이벤트를 만들 때 테넌트 콘텐츠 버킷으로 복사합니다. 커스텀 업로드는 없고, 테넌트는 이미지 assets만 올립니다. JS는 전부 우리 코드입니다.
  • 02·03·04 모두 CloudFront로 서빙합니다. 테넌트마다 distribution 하나(*.{tenant id}.루트도메인), 이벤트는 {event id}.{tenant id}.루트도메인, 경로는 /api/*(ALB)와 /*(테넌트 콘텐츠 S3)로 나눕니다.
  • Redis는 단일 노드 단일 샤드, 스케일 업으로 대응합니다. PoC에서는 EKS Pod로 올립니다.
  • 발급이력은 결과 확정 시 INSERT 한 번이고, SQS와 워커는 쓰지 않습니다.
  • 진입, 번호 수령, 재발급은 Redis 집계 카운터로 셉니다.
  • 사전 스케일링을 합니다. 범위는 미정입니다.
  • 타임아웃은 따로 둡니다.

미정

  • 기획서의 "전체 참여 현황"을 사람별 목록이 아니라 단계별 인원 수치로 해석하는 것에 대한 팀 확인, ERD 4단계 문서와 토큰·세션 Flow 문서 수정
  • 쿠폰 발급 API의 서버 측 입장 자격 검증
  • 테넌트 콘텐츠 버킷이 테넌트마다 하나인지 이벤트마다 하나인지(문서에는 이벤트별 S3 버킷이 승인 때 생성된다고 되어 있음), 그에 따라 호스트 이름의 {event id}로 파일 위치를 고르는 방법 (CloudFront Function과 KeyValueStore가 후보)
  • /api/* 경로 규칙의 세부 설정, 쿼리 문자열을 ALB·CloudFront 로그에서 제외할 수 있는지, 테넌트 exp 권장값
  • 테넌트별 와일드카드 인증서와 DNS를 만드는 시점(테넌트 등록 때), distribution 개수 한도
  • 이미지 업로드의 형식·크기 제한과 안전한 서빙 방식
  • 템플릿을 복사하는 시점(이벤트 승인 때)과, 템플릿을 고쳤을 때 이미 복사된 이벤트에 반영하는 방식
  • 테넌트는 이미지만 쓰고 JS 파일은 덮어쓸 수 없도록 버킷 쓰기 권한을 나누는 방법 (업로드는 우리 파이프라인을 거침)
  • 진입 엔드포인트의 세부 경로 이름 (/api/ 아래)
  • 세션 TTL (대기방 1시간 + 번호표 대기 + 발급 화면 체류 + 여유)와 세션 만료 시 재진입 경로
  • 세션과 user_id를 연결하는 키의 정리 방식
  • 집계 카운터를 MySQL에 언제 어디에 저장할지
  • 지터 2초를 코드에 고정할지 서버가 이벤트별로 내려줄지
  • 서버 시각 기준 카운트다운 보정 방식과 백그라운드 탭 재보정
  • 타임아웃 값과 기준
  • 공개키 캐시 여부와 폐기된 키의 반영 지연
  • 서빙 커서를 올리는 주체, 주기, 한 번에 올릴 칸 수
  • 사전 스케일링의 시점, 트리거, 대상 범위
  • 부하 테스트로 잴 값: 번호표 API Pod 하나와 Redis 노드 하나의 처리 한계
  • 세션의 Redis 자료구조 (Lua가 읽고 쓰기 좋은 해시로 가정)
  • Redis Pod의 배치와 자원: 전용 노드 여부, CPU 요청과 한도(한도를 걸면 스로틀링으로 지연이 튈 수 있음), 영속성 끄기, 이벤트 중 재스케줄 방지
  • 운영 배포의 Redis를 ElastiCache로 옮길지 (PoC의 Redis 한계 측정 결과로 판단)

팀 확인이 필요한 것

  • 발급이력을 결과 확정 시 INSERT 한 번으로 바꾸는 것. 기획서의 "전체 참여 현황"을 사람별 목록이 아니라 단계별 인원 수치로 해석해도 되는지가 핵심입니다.
  • 새로고침과 재시도에 새 번호를 주고 구멍을 허용하는 것.
  • 서버가 시작 전 요청을 거절하는 것과 지터 0~2초(서버 강제 없음).
  • 같은 사용자가 다시 진입하면 기존 세션을 재사용하는 것. 여러 탭이 같은 세션을 공유하고, 번호표는 그래도 매번 새로 받습니다.
  • 테넌트가 user_id를 회원마다 한 번만 만들어 계속 재사용하는 것. 연동 가이드에 고유성, 역산 불가, 이벤트 기간 중 불변을 조건으로 적어야 합니다.
  • JWT를 쿼리(GET)로 받는 것과, 테넌트가 exp를 짧게 잡는 것(연동 가이드에 명시).
  • 세션 ID를 쿠키로 전달하고, 02·03·04를 같은 호스트 아래 경로로 묶는 CloudFront 구성(테넌트별 distribution과 와일드카드). 문서의 도메인 매핑과 인증서 발급 단계가 이 구조(인증서와 DNS는 테넌트 등록 때 한 번)를 전제하는지도 확인해야 합니다.
  • 커스텀 업로드를 없애고 템플릿만 제공하는 것. 이벤트 신청의 화면 설정(UI-TP-09)에서 커스텀 업로드가 빠지고 템플릿 선택과 이미지 업로드만 남는지, ERD의 event_upload와 업로드 검증 파이프라인이 이미지 기준으로 바뀌어야 하는지 확인이 필요합니다.
  • Redis 단일 샤드와 스케일 업, 진입과 번호표 요청의 Lua 처리.
  • 부하 테스트로 스펙을 정하는 방식.
  • 서빙 커서를 누가, 얼마나 자주, 몇 칸씩 올릴지.
