# 폴링 클라이언트 구현 스펙

Hands-off대기방(03 화면) 순번 폴링 — 프론트엔드 구현 담당자용

대기방에서 "내 번호가 언제 되는지"를 확인하는 폴링 로직의 구현 스펙입니다. 백엔드가 내려주는 응답 하나(서빙 커서)와 클라이언트 쪽 분기·간격 로직만 있으면 되고, 커서를 누가 어떻게 증가시키는지는 이 문서의 범위 밖입니다. 궁금한 점은 이 문서로 먼저 확인하고, 그래도 안 풀리면 다란에게 문의해 주세요.

!

품절 플래그(재고 소진 안내)는 이번 구현 범위에서 **제외**하기로 결정했습니다. 아래 스펙에는 품절 관련 분기가 없습니다.

## 1 왜 이렇게 설계했는가

기존 새싹티켓 방식(ZSET + 디스패치 워커가 N명씩 끊어 개인별 알림)은 응답이 사용자마다 달라서 캐시할 수 없었습니다. 이번 설계는 **"서빙 커서"**라는 값 하나(이벤트당 하나, 모든 사용자에게 동일)만 내려주고, 내 번호와의 비교·다음 폴링 시점 결정은 전부 클라이언트가 담당합니다. 응답이 개인화되지 않으므로 CDN에서 짧은 TTL로 캐시할 수 있고, 50,000명이 동시에 폴링해도 origin(API 서버)에 도달하는 요청 수를 크게 줄일 수 있습니다.

## 2 백엔드 API 계약

| 항목 | 값 |
| --- | --- |
| Method / Path | `GET /api/issuance/events/{eventId}/queue/cursor` |
| 인증 | 없음(2026-10-01 변경). CDN 캐시 대상이라 인증하지 않음. 별도 헤더·쿠키 작업 불필요 |
| 응답 본문 | `{"success": true, "data": {"cursor": number}}` — 모든 API 공통 형식(`data` 안에 값). 이벤트별 전역 값, 사용자마다 다르지 않음 (2026-10-01 실제 응답 기준으로 수정) |
| 캐싱 | CloudFront에서 약 1초 캐시됨(`Cache-Control: public, max-age=0, s-maxage=1`). 같은 순간 여러 클라이언트가 동일한 cursor 값을 받는 것이 정상 동작 |
| 커서 역행 | 엣지(CloudFront 서버)마다 캐시가 따로라서 **직전에 받은 값보다 작은 cursor가 올 수 있음** → 지금까지 받은 cursor 중 최댓값만 사용 |
| 에러 응답 | 4xx/5xx는 실제 상태 코드 그대로 옴(index.html로 바뀌지 않음). `res.ok`로 실패를 판단 |
| 내 번호(티켓 번호) | 이 API가 주지 않음 — 번호표 발급 API 응답에서 이미 받아 클라이언트가 들고 있던 값을 그대로 사용 |

즉 클라이언트는 `myTicketNumber`(이미 갖고 있음)와 `cursor`(폴링으로 받음) 두 값만 비교하면 됩니다.

## 3 클라이언트 분기 로직

`maxCursor = max(지금까지 받은 cursor)` — 받은 cursor가 직전 값보다 작으면 무시하고 이전 최댓값을 씁니다.

`gap = myTicketNumber - maxCursor`

- `gap <= 0` → 내 차례입니다. 폴링을 멈추고 발급 화면(04)으로 이동합니다.
- `gap > 0` → 아직 대기 중입니다. 아래 표로 다음 폴링까지의 대기 시간을 정하고 다시 요청합니다.

| gap (내 번호 − 커서) | 다음 폴링 간격 |
| --- | --- |
| 10,000 초과 | 10초 |
| 1,000 \~ 10,000 | 5초 |
| 100 \~ 1,000 | 2초 |
| 100 이하 | 1초 |

간격은 매 응답마다 새로 계산합니다. 이전에 계산해 둔 간격을 재사용하지 않습니다.

## 4 구현 방식 — recursive setTimeout

`setInterval`이 아니라 `setTimeout`을 응답마다 다시 거는 방식으로 구현합니다. 이유: 간격이 매번 바뀌는데(위 표 참고) `setInterval`은 한 번 정한 주기를 바꿀 수 없기 때문입니다.

### React 커스텀 훅 예시

```
function useQueuePolling(eventId, myTicketNumber) {
  const [gap, setGap] = useState(null);
  const timeoutRef = useRef(null);
  const maxCursorRef = useRef(0); // 지금까지 받은 cursor 최댓값 (엣지별 캐시로 인한 역행 방지)

  useEffect(() => {
    let cancelled = false;

    async function poll() {
      try {
        const res = await fetch(`/api/issuance/events/${eventId}/queue/cursor`);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const { data: { cursor } } = await res.json(); // 공통 응답 형식: {success, data: {cursor}}
        if (cancelled) return;

        maxCursorRef.current = Math.max(maxCursorRef.current, cursor);
        const currentGap = myTicketNumber - maxCursorRef.current;
        setGap(currentGap);

        if (currentGap > 0) {
          timeoutRef.current = setTimeout(poll, computeDelay(currentGap));
        }
        // currentGap <= 0 이면 더 폴링하지 않고 종료
        // → 이 값을 보고 호출부에서 04 화면으로 라우팅
      } catch (err) {
        // 네트워크 실패: 동일 간격으로 재시도 (아래 5번 참고)
        if (!cancelled) {
          timeoutRef.current = setTimeout(poll, 2000);
        }
      }
    }

    poll();

    return () => {
      cancelled = true;
      clearTimeout(timeoutRef.current);
    };
  }, [eventId, myTicketNumber]);

  return gap;
}

function computeDelay(gap) {
  if (gap > 10000) return 10000;
  if (gap > 1000)  return 5000;
  if (gap > 100)   return 2000;
  return 1000;
}
```

호출하는 쪽(03 화면 컴포넌트)에서 `gap`이 0 이하가 되는 순간을 감지해 04로 라우팅하면 됩니다.

## 5 체크리스트 / 주의사항

- 언마운트 시 반드시 `clearTimeout`을 호출합니다. 하지 않으면 사용자가 03 화면을 벗어나도 폴링이 백그라운드에서 계속 돕니다.
- 네트워크 요청이 실패하면 즉시 포기하지 말고 동일하거나 짧은 간격으로 재시도합니다. 단, 무한 재시도로 인한 배터리/트래픽 낭비를 막기 위해 연속 실패 횟수에 상한을 두는 것을 권장합니다(예: 5회 연속 실패 시 에러 UI 노출).
- cursor 값은 전역 값입니다. 여러 사용자가 동일한 응답을 받는 것은 버그가 아니라 설계된 동작입니다.
- cursor가 직전 값보다 작게 와도 정상입니다(CDN 엣지마다 캐시가 다름). 항상 지금까지 받은 최댓값(`maxCursorRef`)으로 gap을 계산합니다.
- `fetch`는 4xx/5xx에서도 예외를 던지지 않으므로 `res.ok`를 반드시 확인해 실패로 처리합니다.
- 탭이 백그라운드로 가면 브라우저가 `setTimeout`을 지연시킬 수 있습니다(스로틀링). 치명적인 문제는 아니지만 QA 때 탭 전환 시나리오도 한 번 확인해 주세요.
- 대기방(02 화면)의 카운트다운·지터 로직과는 별개의 코드입니다. 혼동하지 않도록 폴링 훅은 03 화면 진입 이후에만 동작하게 합니다.

## 6 이 문서가 다루지 않는 것

### 범위 밖 (다른 담당자 영역)

- 서빙 커서를 증가시키는 백엔드 로직(락 기반 피기백 또는 시간 함수) — 백엔드 담당
- 재고 소진 시 품절 안내(품절 플래그) — 이번 범위에서 제외하기로 결정
- 발급 화면(04)·쿠폰 발급 API의 서버 측 입장 자격 재검증 — 별도 담당
- 번호표 발급 자체(내 번호를 받아오는 API) — 이미 구현된 별도 플로우

## 7 완료 기준

- gap ≤ 0이 되는 순간 폴링이 멈추고 04 화면으로 전환된다
- gap 구간별로 폴링 간격이 표대로 바뀐다 (Network 탭에서 요청 간격 확인)
- 03 화면을 벗어나면(언마운트) 폴링 요청이 더 이상 나가지 않는다
- 네트워크 요청이 실패해도 화면이 멈추거나 크래시하지 않는다
- 직전보다 작은 cursor를 받아도 gap이 커지지 않는다(최댓값 유지)
