Tetra 발급 플로우 전체 다이어그램

테넌트가 JWT를 서명해 보내는 순간부터 쿠폰 발급 결과가 이력에 남는 순간까지의 흐름입니다. 지금까지 정한 내용을 반영했고, 아직 설계하지 않은 부분(폴링·서빙 커서, 집계 저장)은 점선으로 표시했습니다.

  • 1진입: 대기방이 1시간 전에 열려 5만 명이 고르게 들어온다고 가정하면 초당 약 14건이라 부하가 작습니다. JWT 검증과 세션 생성만 하고 DB에는 쓰지 않습니다.
  • 2번호표 발급: 이 시스템에서 가장 크게 몰리는 지점입니다. 요청 경로에는 Redis Lua 한 번뿐이라 DB와 큐가 없고, 지터가 짧아 순간 피크는 사전 스케일링과 Redis 스케일 업으로 받습니다.
  • ↑사전 스케일링 후보 Pod입니다. 시점, 트리거, 범위는 아직 정하지 않았습니다.
  • 굵은 테두리는 부하 완화 장치(지터)와 원자성이 필요한 재고 Lua입니다.
  • 점선 박스와 화살표는 아직 설계하지 않았거나 방식이 정해지지 않은 부분입니다.

흐름 요약

  1. 테넌트 백엔드가 개인키로 JWT를 서명해 Tetra로 리다이렉트합니다.
  2. API가 MySQL의 공개키로 서명과 만료를 검증하고, Redis에서 jti를 확인한 뒤 세션을 만듭니다. 진입 카운터가 +1 됩니다.
  3. 이벤트 1시간 전에 열린 대기방에서 카운트다운이 끝나면 버튼이 활성화되고, 지터 0~2초 뒤에 03 화면으로 진입해 번호표 API를 호출합니다.
  4. 번호표 API는 서버 시각이 이벤트 시작 전이면 거절하고, 통과하면 Lua 하나로 세션 확인, 번호 채번, 세션 기록, 집계 카운터 갱신을 처리합니다.
  5. 03 화면이 폴링으로 내 번호와 서빙 커서를 비교합니다(설계 예정). 대기자 수가 0이 되면 발급 화면(04)으로 이동합니다.
  6. 04는 테넌트가 올린 정적 페이지입니다. 쿠폰 받기를 누르면 쿠폰 API가 재고 Lua로 중복 확인, 재고 확인, 차감을 한 번에 처리합니다(전체 발급).
  7. 결과가 성공이든 품절이든 발급이력에 행 하나를 INSERT하고 결과 화면으로 응답합니다.

이 그림의 가정

  • 번호표 API는 재시도든 새로고침이든 호출될 때마다 새 번호를 발급합니다. 버려진 번호는 구멍이 되고 서빙 커서는 구멍을 그냥 지나갑니다. 실제 입장 인원은 N × (1 − 구멍 비율)이며, 구멍 비율은 집계 카운터의 재발급 수로 계산합니다.
  • 번호표 API는 서버 시각이 이벤트 시작 시각 전이면 Redis 호출 전에 거절합니다. 거절된 요청은 번호를 소모하지 않습니다.
  • 지터는 0~2초이고 서버가 강제하지 않습니다. 우회하는 요청은 막지 못하는 것을 감수하며, 선착순은 서버 도착 순서 기준으로 2초 안에서는 순서가 섞입니다.
  • 진입은 대기방이 열려 있는 1시간에 고르게 들어온다고 가정합니다. 시작 직전에 쏠리는 경우도 부하 테스트 시나리오에 넣어 확인합니다.
  • Redis는 단일 노드 단일 샤드로 두고 부족하면 노드 사양을 올립니다. 번호표 요청은 성능 목적으로 Lua 하나로 처리하고, 재고 차감 Lua는 원자성 목적으로 씁니다.
  • 쿠폰은 전체 발급이고 이벤트 안의 쿠폰 매수가 모두 같아서 일부만 품절되는 경우가 없습니다. 재고 Lua는 재고 키 하나와 중복 발급 플래그만 다루므로, 여러 재고 키를 한 번에 확인하고 하나라도 부족하면 전체를 실패시키는 로직이 필요 없습니다.
  • 발급이력은 쿠폰 받기 결과가 확정될 때 사용자당 행 하나를 INSERT합니다. 성공과 품절 실패를 모두 기록하고, 세션의 티켓 번호와 대기열 진입 시각을 함께 넣습니다. 진입만 하거나 번호만 받고 나간 사람은 사람별 기록 없이 집계 카운터로만 남깁니다.
  • 근본적인 부하 대응은 부하 테스트로 필요한 스펙을 정하는 방식입니다. 병목으로 확인된 곳만 추가로 고칩니다.

결정된 것과 남은 것

결정

  • 재시도와 새로고침 모두 새 번호를 발급하고 구멍을 허용합니다.
  • 번호표 API가 서버 시각 기준으로 이벤트 시작 전 요청을 거절합니다.
  • 클라이언트 지터를 0~2초로 적용합니다. 서버 강제는 하지 않습니다.
  • Redis는 단일 노드 단일 샤드, 스케일 업으로 대응합니다.
  • 번호표 요청은 Lua 하나로 처리합니다.
  • 발급이력은 결과 확정 시 INSERT 한 번(성공·품절 실패 모두)이고, SQS와 워커는 쓰지 않습니다.
  • 진입, 번호 수령, 재발급은 Redis 집계 카운터로 셉니다.
  • 쿠폰은 전체 발급이고 매수가 모두 같아서, 재고는 이벤트당 카운터 하나로 셉니다.
  • 사전 스케일링을 합니다. 범위는 미정입니다.
  • 타임아웃은 따로 둡니다.

미정

  • 폴링과 서빙 커서: 증가 주체, 주기, 칸 수, 캐시 (나중에 설계)
  • 집계 카운터를 MySQL에 언제 어디에 저장할지
  • 재고가 소진된 뒤 대기 중인 사람에게 바로 품절을 안내할지 (품절 플래그)
  • 03에서 04로 넘어갈 때 세션 전달 방식과 발급 API의 서버 측 입장 자격 검증
  • 지터 2초를 코드에 고정할지 서버가 이벤트별로 내려줄지
  • 서버 시각 기준 카운트다운 보정 방식과 백그라운드 탭 재보정
  • 세션 TTL (대기방 1시간 + 번호표 대기 + 발급 화면 체류 + 여유)
  • 타임아웃 값과 기준
  • 공개키 캐시 여부와 폐기된 키의 반영 지연
  • 사전 스케일링의 시점, 트리거, 대상 범위
  • 부하 테스트로 잴 값: 번호표 API Pod 하나와 Redis 노드 하나의 처리 한계
  • 세션의 Redis 자료구조 (Lua가 읽고 쓰기 좋은 해시로 가정)

팀 확인이 필요한 것

  • 발급이력을 결과 확정 시 INSERT 한 번으로 바꾸는 것. 기획서의 "전체 참여 현황"을 사람별 목록이 아니라 단계별 인원 수치로 해석해도 되는지가 핵심이고, 결정되면 ERD 4단계 문서와 토큰·세션 Flow 문서를 고쳐야 합니다.
  • 새로고침과 재시도에 새 번호를 주고 구멍을 허용하는 것.
  • 서버가 시작 전 요청을 거절하는 것과 지터 0~2초(서버 강제 없음).
  • Redis 단일 노드와 스케일 업, 번호표 요청의 Lua 처리.
  • 부하 테스트로 스펙을 정하는 방식.
  • 이벤트 신청 폼에서 쿠폰 매수가 모두 같도록 보장되는지 (입력 필드를 하나로 하거나 동일 값 검증). 다르게 들어갈 수 있다면 재고 카운터 하나로는 부족합니다.
  • 서빙 커서를 누가, 얼마나 자주, 몇 칸씩 올릴지. DB 쓰기가 방어됐다는 판단이 이 값에 기대고 있습니다.
